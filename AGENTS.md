## Текущий стек

- Node.js 24.22.1+, ESM `.mjs`, встроенная SQLite `node:sqlite`.
- Интерфейс: обычные HTML/CSS/JavaScript в `public/`.
- Внешних npm-зависимостей приложения нет.
- Next.js, React, TypeScript и Cloudflare D1 удалены при прежней переработке.
  Пустые каталоги и игнорируемые кеши старого стека не являются исходниками.
- `dist/` генерируется сборкой. Редактируй исходники, не файлы в `dist/`.

## Что важно сохранить при изменениях

- Деньги — целые копейки. Неизвестная закупочная цена — `null`, не ноль.
- ID магазинов — `0`, `1`, `2`; номера в интерфейсе — `1`, `2`, `3`.
- Менеджер читает и изменяет только свою точку. Своя касса ему доступна;
  закупочные цены, себестоимость и прибыль — нет. Проверки нужны на сервере.
- Проведённые складские документы не редактируются. Возврат связан с продажей.
- Перемещение товара требует приёмки получателем; она может быть частичной.
- Перевод денег — одна запись `cash` с `shop` и `to`, не две независимые операции.
- Изменение состояния и запись ключа идемпотентности должны оставаться в одной
  синхронной транзакции `Store.transaction()` / `BEGIN IMMEDIATE`.
- `apply()` изменяет переданное состояние. При ошибке не сохраняй этот объект:
  HTTP-обработчик работает с копией и откатывает транзакцию целиком.
- Дневные отчёты используют `Europe/Moscow`. Текущая касса и остаток на конец
  выбранного прошлого дня — разные показатели.

## Как продолжать работу

Сначала прочитай `git status --short`, нужные исходники и существующие тесты.
Сохраняй чужие незакоммиченные изменения. Не добавляй новые фреймворки без
практической необходимости для задачи.

Для изменений логики добавляй содержательные проверки соответствующего сценария.
Основные команды — `npm test`, `npm run lint`, `npm run build`; браузерные и
Python-проверки описаны в `docs/DEVELOPMENT.md`. Для правок только документации
достаточно проверить ссылки и согласованность текста с кодом.

Push в `main` автоматически публикует сайт после успешных проверок. Учитывай это
перед push; выполняй публикацию, если она входит в поручение пользователя или
уже разрешена им в текущей сессии. Не сбрасывай рабочую базу и не проводи в ней
тестовые продажи, расходы или переводы для проверки реализации.

Пароли, приватные ключи, SQLite и файлы из `outputs/` / `data/` не должны попадать
в Git или вывод инструментов. Локальные сведения о доступе находятся в
игнорируемом `outputs/admin-access.txt`; на другом компьютере файла может не быть.

После изменения поведения обновляй соответствующий раздел документации.
