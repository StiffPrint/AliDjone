# GitHub Actions и публикация

Репозиторий: https://github.com/StiffPrint/AliDjone
Сайт: https://alijhone.store
Workflow: `.github/workflows/ci-cd.yml`.

Pull request запускает Node.js 24.22.1, складские/HTTP/импортные тесты, проверки учётных записей, синтаксиса JS и shell, Python-тесты распаковки и отката, браузерные сценарии и сборку. Playwright 1.63.0 установлен отдельно от приложения. GitHub Actions закреплены по SHA.

После успешных проверок push в `main` автоматически публикует тот же архив. Ручной запуск workflow для `main` также выполняет проверки и публикацию. Другие ветки не публикуются. Одновременные деплои исключены; устаревшие коммиты пропускаются перед отправкой.

Секреты репозитория:

- `ALIDJONE_DEPLOY_HOST`
- `ALIDJONE_DEPLOY_USER`
- `ALIDJONE_DEPLOY_SSH_KEY`
- `ALIDJONE_DEPLOY_KNOWN_HOSTS`

GitHub не получает личный SSH-ключ администратора. Используется отдельная учётная запись `alidjone-deploy`. Её ключ разрешает только команду `deploy` через root-owned `/usr/local/libexec/alidjone-ssh-entrypoint`. Sudo разрешает только `/usr/local/sbin/alidjone-receive-release` без аргументов. SSH host key закреплён через known_hosts; произвольные команды и перенаправление портов запрещены.

Серверный receiver проверяет архив, запрещает ссылки, выход за каталог и запись базы, затем запускает тесты загруженного кода от `nobody`, который не имеет доступа к рабочей SQLite. Перед переключением создаётся проверенная резервная копия через `alidjone-backup.service`. Новая версия устанавливается в отдельный каталог `/opt/alidjone/releases/`, ссылка `current` заменяется атомарно, перезапускается только `alidjone.service`.

Если запуск или проверка `/healthz` с SHA коммита не проходят, сервер автоматически возвращает предыдущую ссылку и перезапускает прежнюю версию. После этого CI проверяет точный SHA через публичный HTTPS. База `/var/lib/alidjone/warehouse.sqlite`, файл окружения и конфигурация Nginx в архив не входят. Автоматическое восстановление базы из резервной копии не выполняется.

Первичная установка receiver и SSH-ограничений выполняется администратором сервера; обычные деплои их не перезаписывают. При изменении `deploy/receive-release.py` или `deploy/ssh-entrypoint.sh` администратор обновляет соответствующие root-owned копии отдельно.

Проверить активную версию:

```sh
curl -fsS https://alijhone.store/healthz
gh run list --repo StiffPrint/AliDjone --workflow ci-cd.yml
ssh server2 'readlink -f /opt/alidjone/current; systemctl is-active alidjone.service'
```

Ручной откат к известному каталогу релиза выполняется администратором через атомарную замену `current` и перезапуск службы. Старые релизы автоматически не удаляются, чтобы сохранять возможность отката.

Аккаунты создаются через интерфейс администратора либо локальную команду `scripts/provision-staff.mjs`, которая принимает массив JSON через stdin и требует DATABASE_PATH. Допустимы логины и email; регистр логина не учитывается. Обычно пароль должен содержать от 12 символов. Явный флаг `--allow-short-test-passwords` предназначен только для оговорённых пробных аккаунтов; HTTP API этим исключением не пользуется. Пароли и хеши не печатаются. Повторный запуск обновляет аккаунт по логину и отзывает его сессии. `replaceLogin` позволяет переименовать существующий аккаунт с сохранением его ID и истории.

Защита ветки main/правила GitHub environment требуют прав администратора репозитория. Аккаунт, выполнявший настройку, имеет WRITE, поэтому эти правила не менялись. Публикация ограничена main самим workflow.
