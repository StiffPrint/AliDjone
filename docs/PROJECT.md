# Проект: что здесь работает и где искать код

Сверено с реализацией 1 ноября 2026. Базовый коммит функциональности — `074c2c0`;
новые изменения проверяй по `git log` и исходникам. Это описание реализации,
а не список ещё не сделанных обещаний.

## Назначение

АлиДжон Store ведёт складской учёт телефонов и аксессуаров в трёх магазинах,
продажи, возвраты, перемещения и наличную кассу. Телефоны учитываются по
серийным номерам, аксессуары — по количеству и закупочным партиям FIFO.
Это оперативный учёт, без налоговой и бухгалтерской отчётности.

Администратор видит на главной три карточки магазинов. Внутри точки — её склад,
касса и показатели за выбранный день. Контекст магазина сохраняется при переходе
между разделами. Есть режим всех магазинов и отчёт за всё время.

### Магазины и пользователи

| ID в данных | Номер в интерфейсе | Название в `fresh()` | Созданный логин |
|---|---|---|---|
| `0` | Магазин 1 | Островок | `Store 1` |
| `1` | Магазин 2 | Центральный | `Store 2` |
| `2` | Магазин 3 | Магазин 2 | `Store 3` |

Последнее название историческое: строка «Магазин 2» — имя третьей точки,
а не её индекс. Имена задаются `fresh().shops` в `lib/warehouse.mjs` и не хранятся
отдельной таблицей. Не меняй порядок массива: документы ссылаются на его индексы.
Логины регистронезависимы, поэтому `Store 1` сохраняется как `store 1`.
На рабочем сайте также создан администратор с логином `admin`. Паролей в Git нет.

| Возможность | `admin` | `leader` | `manager` |
|---|---|---|---|
| Работа со складами | Все точки | Все точки | Только своя |
| Каталог и закупочные цены | Да | Да | Чтение каталога без закупки |
| Касса, дневная выручка, расходы | Все точки | Все точки | Только своя |
| Себестоимость и прибыль | Да | Да | Нет |
| Начальный остаток кассы | Да | Да | Нет |
| Перевод денег | Из любой кассы | Из любой кассы | Только из своей |
| Управление сотрудниками | Да | Нет | Нет |

Входящие перемещения товара и входящие переводы денег доступны получателю.
Менеджер не получает документы и баланс чужой кассы целиком.

## Как проходит изменение данных

```text
Форма в public/app.js
  → POST с cookie, Origin, CSRF и Idempotency-Key
  → server/server.mjs проверяет сессию и запрос
  → BEGIN IMMEDIATE
  → Store.read() → structuredClone(before)
  → apply() / cashChange() / staffChange()
  → Store.save(before, state) + запись operations
  → COMMIT
```

При исключении транзакция откатывается. В частности, ошибка во второй строке
документа не должна сохранить списание из первой строки. Пароль хешируется
асинхронно до транзакции; внутри транзакции заново проверяются полномочия.
Один ключ с тем же телом возвращает прежний результат, а с другим телом — `409`.

`view()` формирует доступную пользователю копию склада; `finance()` отдельно
фильтрует кассу и скрывает от менеджера финансовые поля с закупкой/прибылью.
Скрытия кнопок на клиенте для ограничения доступа недостаточно.

## Данные и правила учёта

### SQLite

У сущностей отдельные строки SQL с JSON в `payload`; это не один JSON всей базы.
Таблицы: `products`, `units`, `documents`, `lines`, `balances`, `staff`, `audit`,
`lots`, `cash`, `sessions`, `operations`. Строки документов находятся в `lines`.
У `staff` пароль хранится отдельно от публичного `payload` в `password_hash`.
Уникальные нормализованные штрихкоды, серийники и логины защищены также SQLite.

`Store.save()` сравнивает снимки и сохраняет изменения, но не является общей
системой удаления сущностей. Из строк удаляются убранные строки документов.
Полноценного механизма миграций схемы сейчас нет; изменение схемы требует
отдельного плана совместимости с существующей базой и откатом к старому коду.

### Склад

- `receipt`: до проведения — черновик; после проведения увеличивает остаток.
- `sale`: списывает доступный товар своей точки, фиксирует цену и себестоимость.
- `transfer`: отправка убирает товар из доступного остатка. Статусы:
  `draft → in_transit → partial → received`; частичный шаг необязателен.
- `accept` передаёт **суммарно принятое количество** и накопленный список
  `serial_ids`, включая ранее принятые номера. Это не добавка к прошлому запросу.
- `customer_return`: связан с проведённой продажей и её строкой, оформляется
  на исходной точке. Нельзя вернуть больше проданного или повторно вернуть
  тот же экземпляр по той же продаже.
- `supplier_return` и `writeoff` требуют причину.
- Отменяется только черновик. Повторное проведение не списывает товар ещё раз.

Для телефонов `units` содержит экземпляр с `product`, `serial`, `shop`, `status`
и `buy`. Доступность: `available`; проданный — `sold`; в пути — `transit` с
`shop: null` и ссылкой `transfer`. Другие конечные статусы — `written_off`,
`supplier_return`. `sale` у проданного экземпляра связывает его с продажей.

`balances[productId]` — массив трёх количеств. Он используется для аксессуаров
и прежних остатков телефонов без номеров. `qty()` складывает количественный
остаток и доступные номерные экземпляры. `attach_legacy` присваивает номера
прежнему остатку, не увеличивая общее количество.

Аксессуары списываются по `lots` FIFO. Прежний остаток без партий вычисляется как
разность `balances` и учтённых партий и расходуется первым. Не создавай для него
партию в конце очереди: это уже приводило к неправильной себестоимости после
следующего запроса и открытия SQLite заново.

### Касса и отчёт за день

Суммы и цены — целые копейки, количества — целые числа. `null` означает
неизвестную закупку; ноль означает известную нулевую цену.

`cash` хранит ручные операции: `opening`, `deposit`, `withdrawal`, `expense`,
`transfer`. Продажи и возвраты автоматически участвуют в кассе через документы;
не создавай для них дополнительные ручные записи, иначе деньги удвоятся.
Карта влияет на выручку, но не на наличную кассу. Возврат наследует оплату продажи.

Перевод денег — одна запись с `shop` отправителя и `to` получателя. Она сразу
дебетует одну кассу и кредитует другую; дополнительного подтверждения получателем
для денег сейчас нет. Изъятие, расход и перевод проверяют текущий наличный остаток.
Переводы и внесения не создают прибыль; расходы её уменьшают.

`finance(state, user, {shop, date})` принимает `date` в формате `YYYY-MM-DD`.
Без даты отчёт строится за всё время. Границы дня — `Europe/Moscow`.

| Поле | Что означает |
|---|---|
| `cash` | Наличные сейчас, по всей истории независимо от выбранной даты |
| `cashOpening` | Остаток до начала выбранного дня; в отчёте за всё время — 0 |
| `cashMovement` | Изменение наличных за период |
| `cashClosing` | Остаток на конец выбранного дня / периода |
| `cashSales`, `cardSales` | Продажи за период минус возвраты по способу оплаты |
| `inventoryUnits` | Текущий товарный остаток, не исторический остаток за дату |
| `profit` | Прибыль; `null`, если нет достоверной себестоимости; менеджеру не выдаётся |

## Границы реализации

Сервер читает состояние в память и работает с копией на каждую операцию.
Пагинации больших складов и выборочного SQL-учёта пока нет. Есть ограничения
100 000 товаров/документов для действий и 500 строк в документе; это защитные
границы, а не результат нагрузочного теста. Дневного снимка склада, закрытия смен,
эквайринга и фискальных чеков нет. Не выдавай текущий склад за исторический отчёт.
